# Coverage & Freshness: plan

## Stack found in the repo

- Language: Python 3 (`pyproject.toml`), FastAPI (`src/riskpatch/api/`), server-rendered HTML built with f-strings in `src/riskpatch/ui.py` (no template engine, no JS framework). Shared CSS tokens are defined in `ui.py` as `:root` variables (`--bg`, `--panel`, `--teal`, `--blue`, `--red`, `--amber`, `--green`, `--slate`, `--muted`). The mockup colors differ slightly; I will map the mockup to these tokens instead of adding a second palette.
- Database: SQLite via `sqlite3` (`src/riskpatch/db.py`), WAL-style connections, `tx()` helper, `now_iso()` returning UTC with `Z`.
- Migrations: numbered SQL files in `src/riskpatch/migrations/`, currently `0001` to `0010`, applied by `db.migrate()` with a `schema_migrations` table. Schema version reported by `/api/v1/ready` is 10.
- Job runner: `jobs` table with dedupe keys and leases (`src/riskpatch/jobs.py`). Types: `cve_sync`, `analysis`, `manual_*`, `report_export`. `enqueue()` already returns an existing queued or running job for the same target, which covers idempotency for refresh.
- Scheduler: `job_schedules` table driven by `scheduler.tick()`, dedupe by time bucket. A separate `worker` container runs `scheduler.worker()`.
- Auth: API tokens with scopes `read`, `ingest`, `operate`, `admin` (`src/riskpatch/auth.py`). UI uses a cookie session with a CSRF token from `auth.csrf_for`. There is no separate "operator" role; `operate` is the operator scope.
- Feed sync: `src/riskpatch/cvesync.py` with providers in `src/riskpatch/providers/`, status in `provider_status`.
- Alerts: `alerts` table, workflow statuses open, acknowledged, closed; generated by `src/riskpatch/alerts.py` and `analysis.sync_alerts`.
- Collector: Go module in `collector/` (go 1.18, installed toolchain is 1.18.1). Currently a one-shot snapshot uploader (`collector/cmd/riskpatch-collector/main.go`, `collector/internal/collect/collect.go`) using dpkg/rpm, runtimes, listeners, services, and php ini values. No enrollment, heartbeat, spool, or daemon.

## Decisions I made (where the spec was open)

- D1. Product name and route. Constant `COVERAGE_PAGE = {"title": "Coverage & Freshness", "subtitle": "Cache state, scan progress, and result freshness", "label": "Coverage", "path": "/ui/coverage"}` in one module. Sidebar entry after Jobs.
- D2. "Assets reporting" definition. The spec says "heartbeat in the last 24h", but Overview today uses `snapshots.received_at` in the last 24h, and rule 3 requires the two pages to match. Plan: introduce one function `assets_reporting(conn, ws, now)` that returns the count using `max(last_heartbeat_at, latest snapshot received_at)` and use it on both pages. Until Phase 3 there is no heartbeat, so the value equals today's Overview value. This is a change to Overview only after the heartbeat exists. Needs your approval.
- D2 (approved). One shared function `assets_reporting(conn, ws, now)` returns the count of assets whose `max(last_heartbeat_at, latest snapshot received_at)` is within 24h. Overview and Coverage both call it. Until heartbeats exist, the value equals today's Overview number.
- D3 (approved). Create `refresh_jobs` as the spec says. The existing job runner writes a `refresh_jobs` row for each refresh-type job (`cve_sync`, `analysis`, new `freshness_refresh`). `jobs` stays unchanged.
- D4. Layer registry in code plus a `cache_layers` table. The code registry defines the four layers and their default TTLs. The table stores operator overrides in `ttl_seconds`. Config lives in `system_settings` (existing) so no new config file.
- D5. Entry model. `cache_entries` is seeded from the registry plus existing rows: one entry per feed source (`provider_status`), one for the CVE index, one per asset (inventory), one per asset (correlation). Entries are created by the state engine, not by hand.
- D6. State engine uses an injectable clock: `now_fn` parameter, default `lambda: datetime.now(timezone.utc)`. All TTL comparisons go through it. Tests use a fake clock.
- D7. Retry policy. `refresh_jobs.max_retries` defaults to 3 (same as `jobs.MAX_ATTEMPTS`). Backoff = `base * 2**attempt` with base 60 seconds, capped at 1 hour. Dead-letter = `dead_lettered=1` and entry state `failed`.
- D8. Invalidation triggers status today: TTL expiry = Detect only; the rest Not built; manual refresh becomes Built in Phase 1. The registry is the only source for the page.
- D9. Capabilities for "Gaps and next steps" live in code with `shipped` and `tested` flags. A flag is set to true only in the same change that adds the feature and its test.

## Phases adapted to the repo

- Phase 0 (this change): `docs/coverage-freshness/DATA-MAPPING.md` and this `PLAN.md`. Docs only.
- Phase 1: migration `0011_coverage_freshness.sql` (additive: new tables and new nullable columns on `assets`), state engine module `src/riskpatch/freshness/` (registry, engine, clock), API routes in `api/app.py` (`/api/freshness/*`, operate scope for POSTs, audit events), refresh jobs wired into `jobs.run_job`. Tests: state engine with fake clock, API auth and idempotency, migration applies on an existing DB.
- Phase 2: UI in `ui.py`: route, header with buttons (POST via existing `check_csrf` pattern, `operate` scope, hidden for read-only users), tabs via `?tab=`, KPI cards, layers card, executive and technical sections, using the existing CSS classes and tokens. Reconciliation test against `dashboard_stats`.
- Phase 3: collector, binary only, scheduled by Ansible/AWX (`ansible/collect-and-send.yml`). Scope:
  - Keep the one-shot binary model. No daemon, no internal scheduler, no systemd unit, no install script, no `.deb`/`.rpm`. Periodic runs are an AWX schedule.
  - Add a heartbeat mode (`-mode heartbeat`, small payload, hash only) and an inventory mode (`-mode inventory`, full package list). The same playbook runs both on different AWX schedules.
  - Add enrollment (`enroll` exchanges a single-use token for a per-agent credential) and server endpoints `POST /api/v1/collector/enroll`, `/heartbeat`, `/inventory`. Credentials are revocable per asset.
  - Keep a spool directory with a size cap for runs that cannot reach the server, flushed in order on the next run.
  - Keep the existing `php -r` ini collection as-is (approved). Document it in the security model.
  - Distro parser tests with fixtures for Ubuntu 22.04 and 24.04, Debian 12, Amazon Linux 2023, RHEL 9. The container-per-distro integration test needs Docker images I will pull, which I can do only with your go-ahead.
- Phase 4: event-driven invalidation (KEV and CVE sync hook, inventory hash change), heartbeat-silence alert and stale-data alert through `alerts`.
- Phase 5: remaining tests, docs `docs/coverage-freshness/README.md`, screenshot comparison, seed script (dev-only, never run automatically), grep check for hardcoded numbers.
